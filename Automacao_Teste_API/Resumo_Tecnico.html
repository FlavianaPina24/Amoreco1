Resumo Técnico do Projeto de Automação de API

Este documento descreve a arquitetura, as tecnologias e as capacidades da plataforma de testes de API que desenvolvemos, desde o seu início como um "projeto zero" até a sua forma final como uma robusta ferramenta de simulação e validação.

1. Tecnologias Utilizadas

O projeto foi construído sobre uma base sólida de tecnologias padrão de mercado para testes em Java:

  • Linguagem: Java 11
  • Framework de Testes BDD: Cucumber 7, utilizando a sintaxe Gherkin para escrever os cenários de teste em linguagem natural (.feature files).
  • Executor de Testes: JUnit 5, que serve como a "ignição" para o Cucumber.
  • Cliente HTTP: RestAssured 5, utilizado para fazer as chamadas de API (POST, GET, PUT, DELETE) e para validar as respostas.
  • Servidor de Mock: WireMock 2, a estrela do nosso ambiente de testes local. Ele nos permite simular o comportamento de APIs de backend de forma controlada.
  • Manipulação de JSON: Jackson (ObjectMapper), para serializar e desserializar objetos Java de/para JSON.
  • Gerador de Relatórios: Masterthought Cucumber Reporting, a nossa "galeria de arte", que gera os dashboards em HTML com as evidências de cada teste.

2. Arquitetura e Estratégia de Testes ("O Que Fizemos")

A nossa estratégia foi a da evolução incremental e isolamento de responsabilidades. Em vez de um único bloco monolítico, nós construímos múltiplos "prédios" de teste independentes, cada um com seu propósito:

O "Caçador" (LocalApiTests.feature)

  • Propósito: Simular um serviço de busca de clientes.
  • Como Funciona: Usa um WireMockServer para interceptar chamadas a /v1/cliente/dados. A lógica de negócio (encontrar um usuário na MassaDeDados ou retornar 404) está embutida no step @Given.

O "Validador" (DocumentValidationTests.feature)

  • Propósito: Simular um microsserviço focado exclusivamente na validação de regras de negócio de documentos (CPF/CNPJ).
  • Como Funciona: Usa um WireMockServer para simular o endpoint /v1/documento/validar. A lógica de validação (tamanho, caracteres permitidos) está no @Given, que configura a resposta (200 OK ou 400 Bad Request) de acordo com o documento de entrada.

A "Estação Espacial" / "Painel de Controle" (MainBusinessFlows.feature)

  • Propósito: Nossa arquitetura mais avançada, projetada para testar fluxos de negócio completos (CRUD) de forma controlada e data-driven.
  • Como Funciona:
    • Data-Driven: A tabela Examples se tornou um "Painel de Controle", onde cada linha representa um fluxo completo, controlado pela coluna acao.
    • Banco de Dados em Memória: Utiliza um HashMap estático para simular um banco de dados, permitindo que os testes tenham "memória".
    • Flexibilidade: Permite que você ative ou desative fluxos de teste complexos apenas comentando ou descomentando linhas na tabela Examples, sem tocar no código Java.

Decisões Arquiteturais Críticas que Garantiram a Estabilidade:

  • Isolamento com Tags: Cada grupo de teste (@local, @local-validation, @main-flow) tem sua própria tag, o que nos permite ter @Before e @After hooks específicos para cada um.
  • RestAssured.reset(): A "cura definitiva". Este comando, colocado no início de cada @Before dos nossos testes locais, limpa qualquer configuração global "vazada" dos testes da API real, eliminando os erros de Connection reset e timeout.
  • Portas Dinâmicas (new WireMockServer()): Deixamos o WireMock escolher uma porta livre a cada cenário, evitando o erro Connection refused.

3. Capacidades da Nossa API Simulada ("O Que Nossa API Faz")

O nosso ambiente de testes local agora simula um ecossistema de microsserviços com as seguintes capacidades:

Serviço de Busca de Cliente (/v1/cliente/dados)

  • Recebe um POST com um {"documento": "..."}.
  • Responde com o User completo (JSON) se encontrado (200 OK) ou com 404 Not Found.

Serviço de Validação de Documento (/v1/documento/validar)

  • Recebe um POST com um {"documento": "..."}.
  • Valida regras de negócio como tamanho e caracteres permitidos.
  • Responde com 200 OK se o formato for válido ou 400 Bad Request se for inválido.

Serviço de Persistência de Cliente (/v1/clientes)

  • POST /v1/clientes: Cria um novo cliente no "banco" em memória e retorna 201 Created.
  • GET /v1/clientes/{id}: Busca um cliente pelo ID e o retorna (200 OK) ou retorna 404 Not Found.
  • PUT /v1/clientes/{id}: Altera os dados de um cliente e retorna 200 OK.
  • DELETE /v1/clientes/{id}: Remove um cliente do "banco" e retorna 204 No Content.

Conclusão

O projeto evoluiu de um simples teste de API para uma plataforma de automação completa e robusta. A arquitetura final, guiada pela sua visão de controle e clareza, nos permite testar desde regras de negócio unitárias até fluxos de ponta a ponta, tudo de forma isolada, estável e com evidências perfeitas.
